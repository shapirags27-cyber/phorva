01


        
Abstract


        

          Autonomous software increasingly interacts directly with blockchain systems.
        


        

          An AI agent can swap, provide liquidity, move funds, interact with protocol,
          execute prediction-market position, rebalance treasury, etc.
        


        

          Valid signature does not necessarily mean action is valid.
        


        

          Agent can have legitimate authority but execute wrong transaction,
          exceed amount, wrong contract/function/token/protocol, violate policy,
          manipulated instructions, final state mismatch.
        


        

          Traditional auth asks who allowed to act; PHORVA adds what authorized,
          transaction representation, policy, outcome.
        


        

          PHORVA is onchain verification and authorization layer between applications
          and execution systems.
        


        
Identity → Intent → Policy → Risk → Authorization → Execution Verification → Evidence / Receipt


        

          PHORVA doesn’t replace wallets, protocols, execution systems, autonomous agents.
        


        

          Phorva decides whether it’s allowed to happen.
        


      



      
      


        
02


        
Problem


        

          Autonomous execution creates new security boundary.
        


        

          Traditional human loop:
        


        
Select action → Review transaction → Sign → Submit


        

          Autonomous:
        


        
Observe → Reason → Plan → Select tool → Construct tx → Sign → Broadcast


        

          Gap between intended and actual calldata.
        


        

          Research note about authorization/policy/key compromise/adversarial/multi-agent security.
        


      



      
      


        
03


        
Verification Gap


        

          Example intent swap 300 USDC for ETH, policy max 500,
          actual tx 3,000 USDC.
        


        

          Signature/wallet/contract/protocol can be legitimate but execution mismatches intent.
        


        
Intent:
Swap 300 USDC for ETH

Policy:
Maximum transaction = 500 USDC

Actual transaction:
3,000 USDC


        

          PHORVA evaluates declared intent, policy, risk, transaction semantics,
          parameters, authorization and allow/block.

What PHORVA Is


        

          Execution-security and verification infrastructure.
        


        

          Verifies agent identity, application/project identity, declared intent,
          execution type, transaction parameters, protocol, target contract,
          function selector, policy, risk, capability authorization,
          transaction security, execution path, final state.
        


        

          Can produce structured verification evidence.

What PHORVA Is Not


        
    
          
  • 
            Not an agent wallet.
            Existing wallet/signer/custody remains.
          
    • 

          
  • 
            Not an AI agent.
            Agent decides objective, PHORVA verifies.
          
    • 

          
  • 
            Not destination app.
            Activity stays in original app
            (prediction market, Uniswap etc.).
          
    • 

          
  • 
            Not a prover network.
            PHORVA defines semantics, external providers can provide
            proving/verification infrastructure.

Core Security Model


        
WHO → Identity

WHAT → Intent

UNDER WHAT CONDITIONS → Policy

HOW RISKY → Risk

IS IT PERMITTED → Authorization

DID IT ACTUALLY HAPPEN CORRECTLY → Execution Verification

CAN WE PROVE/AUDIT IT → Evidence


        

          Four dimensions:
          authority, conditions, execution, outcome.

          Associates verification requests with authenticated project/application
          and agent.
        


        

          Project has API credentials, agents, policies, verification history, usage.

  "capabilities": ["swap"]
}


        

          Caller-supplied identity does not automatically become authority;
          registered server-side project/agent state determines authorization.

          Capabilities define action class allowed.
        


        

          Example agent with swap capability.

  "id": "trading-agent-01",

          Transfer can fail capability boundary.

  "token": "USDC",
  "outputToken": "ETH"

          and the authorization decision fails.

          The execution therefore fails authorization.

    Single tx may be below max but collective behavior
    can violate velocity/exposure.

450

    while the collective behavior can violate velocity.
  


  

    Can trigger velocity violation → quarantine →
    future execution blocked/reviewed.
  


  

    Critical risk can trigger quarantine.

    Future blockchain systems increasingly autonomous:
    control assets, call protocols, strategies, payments,
    liquidity, markets, treasuries, coordination.
  


  

    The question changes from:
  


  

    “Did someone sign the transaction?”
  


  

    to:
  


  

    “Was this exact action authorized, did it satisfy conditions,
    and did execution produce intended result?”
  


  

    Phorva infrastructure answers this.
